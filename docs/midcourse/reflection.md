# Reflection

For this project I used Claude as my AI coding assistant throughout — for planning the two features (Tags and Search + Combined Filters), generating the initial FastAPI/Pydantic model, storage, and route code, writing the pytest test suites, and drafting the frontend HTML/CSS/JS for the modal, tag chips, and search/filter bar. I worked through each layer in small steps: model changes first, then storage, then the route, then tests, then frontend — verifying with `pytest` after each backend change and manual browser checks after each frontend change, rather than accepting a large batch of generated code at once.

One place AI genuinely helped was the combined-filter logic for Search. I explicitly constrained the prompt to require AND logic across all filters (search, status, priority, tag) rather than leaving it to guesswork, and the generated code implemented this correctly using sequential list-comprehension narrowing. I then wrote a dedicated test, `test_combined_filters_use_and_logic_not_or`, and proved it with a Break Test — deliberately switching the logic to OR and confirming the test caught the regression — which gave me real confidence the behavior was both correct and protected against future changes.

The part that slowed me down most wasn't actually the AI-generated code — it was environment friction on my end: PowerShell execution policy blocking script activation, losing track of which terminal window had the virtual environment active versus which was running the server, and a nested folder structure from extracting a zip that caused several "file not found" errors. None of that was a code problem, but it consumed a large share of the session and is worth remembering for next time: confirm the working directory and active environment before running any command, rather than assuming.

The clearest example of my review changing the result was the tag-filtering behavior. The AI's first implementation of the tag filter did an exact, case-insensitive match — which was a reasonable literal answer to the prompt I gave, but I only caught the problem by actually using the UI: typing part of a tag name into the filter box showed no results, while the same partial typing worked fine in the Search box. That inconsistency wouldn't have shown up in the pytest suite as originally written, since I hadn't thought to test partial matching until I noticed the UX gap myself. I changed the filter logic to partial match, added a new test to lock in the corrected behavior, and documented the decision in `mini-adr.md`. It was a good reminder that passing tests only prove what you thought to test for — manually using the feature the way a real user would is what actually surfaced this gap.
